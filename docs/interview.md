# Interview with the author

## What specific task did you want to tackle when you came up with Git-on?

I wasn't trying to solve a specific task, but rather to address the problem of
trust to some extent. When the code in front of us is generated by AI without
human review, and the tests it passes were also generated by AI, where does trust
in that code come from?

That led to the idea that it would be useful to take fixed revisions by hash,
carry out all kinds of checks, observe them running in practice, and examine the
logs. Once enough trust has built up, we can sign the revision and run only signed
(verified) revisions in production, with the ability to quickly roll back to a
previously verified revision.

I would add that another problem with languages such as Python is the risk of
source files being replaced during execution. Mounting the repository with
read-only access also protects the code being run from a malicious unprivileged
process.

## Should Git-on itself keep a history of verified revisions and choose which revision to roll back to, or should the choice always be left to the user or an external system?

Storing verified revisions belongs to Git. Rollbacks and updates are outside
Git-on's responsibilities.

## Should Git-on protect source files from processes running as the same OS user, or only from processes running as another unprivileged user?

From processes running as the same OS user. Ordinary permissions can protect
against other users.

## Should Git-on's protection cover only source-file replacement, or also interference with the running process's memory, for example through a debugger?

Git-on solves this problem in a model where another unprivileged process cannot
attach a debugger to our process or interfere with its memory.

On Linux systems with Yama, `ptrace_scope=1` can be enabled if it is not already
enabled, to restrict debugger attachment by a neighboring process running as the
same user.

## How much additional time and RAM usage do you consider acceptable when running a command through Git-on compared with running the same command from an ordinary local copy of the repository?

*You can answer qualitatively, without specific numbers.*

Overhead should be minimized. File reads should be lazy, so that running a script
from a large monorepo can happen almost instantly without materializing the whole
repository before execution.

Large files also need to be taken into account. Preferably, they should be read
and written to the cache as streams rather than loaded entirely into RAM.

If the backend supports passthrough with the required permissions and it speeds
up file operations, that mode should be used.

## If a platform cannot read the repository lazily and running a command requires materializing it in full, should Git-on refuse to run, or allow that mode only when the user explicitly chooses it?

Git-on should not refuse to run if it can execute the command on the specified
tree while respecting the write policy. It should operate on a best-effort basis.

## Should Git-on tell users when it uses a slower fallback, or should this remain unnoticed when the command runs successfully?

By default, Git-on should not complain to the user, but it makes sense to show an
animated status during a lengthy materialization when running in a terminal. The
status should disappear before the command starts.

## Once Git-on has external users, is it acceptable to introduce breaking interface changes for simplicity, or should keeping existing commands working take priority?

Changes to Git-on should follow standard semantic versioning and deprecation
practices so that users know what to expect.
